### Added
- **Attack paths are an engine result.**
  `report.attack_paths` now holds the paths from the internet to the data, in JSON as `attack_paths`, and the CLI gate counts them.
  A path is a chain of resources an attacker can follow over directed reachability edges, from the synthetic `internet` node to a crown jewel: a data store or secret store, a role that may do everything, a Kubernetes Secret, a cluster-admin grant or an MCP server that reads private data or credential paths.
  Containment and dependency edges are never followed, so a VPC that merely contains a public subnet and a private one joins nothing.
  A path ends at the first crown jewel it reaches, runs through at most 8 edges and is simple (no node twice).
  Monitoring nodes, networks, namespaces, ConfigMaps, the companion resources that configure a store and Dockerfile instructions are never targets and never part of a path.
- **Each hop says what enables it and how it is reached.**
  A hop lists `enabled_by`, the ids of the rule, secret and scanner findings on its resource and on the nodes its edge names in `via` (the security group whose rule admits the traffic, the listener, the role binding), worst first.
  Repudiation, denial of service and informational findings do not help an attacker move and are not enabling, and neither are boundary or LLM findings.
  A path is kept only when some finding enables a hop or the target, so an architecture with nothing wrong on its way to the data has no attack path.
  The enabling findings get the path id in `path_ids`.
  `via` on a hop gives the edge to the next hop: its `source`, `protocol`, `ports`, `world_open`, `relation`, `access` and `actions`, and `definite: false` when the edge is a guess.
- **Techniques per step.**
  A hop lists the ATT&CK techniques of the step that reaches it, from `engine.mitre.PATH_TECHNIQUES`: T1190 for an exposed application, T1133 for an exposed remote administration port (22, 23, 3389, 5900, 5985, 5986), T1552.005 where the hop's instance allows IMDSv1, T1078.004 for a role assumed, T1530 for cloud storage read, T1552.007 for a Kubernetes Secret read, T1611 for a privileged container, T1659 for untrusted content that reaches an agent and T1005 and T1552.001 for an MCP server that reads files and credential paths.
  The path lists their union and the tactics that follow.
- **Severity, score and order of a path.**
  The severity is the worst effective severity of the enabling findings, one level higher when the target is a data store tagged with a sensitive classification, and never above `high` unless every edge of the path is definite.
  The score is `severity * 1.5` (info 0 to critical 6), plus 2 when the first edge is open to the whole internet, plus `(8 - edges) * 0.2` for a short path, plus up to 0.6 for the target.
  Paths are ordered by score, then severity, then length, then id, which hashes the node sequence.
  Each carries one generated sentence as its rationale.
  Routes that differ only by the instance of a counted resource (`app[0]` and `app[1]`) are one path with `alternatives` counting the others, a path that is part of a longer one is dropped, and at most 5 routes per target and 100 paths are kept.
  The search is bounded (5,000 routes, 250,000 steps) and records a `paths.search_truncated` warning when it stops early.
- **The reachability layer (`ir/reachability.py`).**
  It runs after exposure and adds `network_flow`, `data_flow` and `iam_binding` edges in the direction traffic or authority travels, each with `source`, `via`, `protocol`, `ports`, `world_open` and `definite`, and creates the `internet` node only when an edge starts there.
  AWS security groups: a world-open ingress rule gives `internet -> X` for every resource X attached to the group that is reachable from outside (a public address in a public subnet, an internet-facing load balancer, a publicly accessible database), and a rule that names another group gives an edge from every member of that group to every member of this one, with the rule's protocol and port range.
  A world-open group on an instance in a private subnet adds nothing.
  Nested ingress blocks, `aws_security_group_rule` and `aws_vpc_security_group_ingress_rule` give the same edges, egress rules are ignored and a Lambda function can send to a group but never receive from one.
  Load balancers: `lb -> target` for the targets of the target groups the listeners and listener rules forward to (attachments, Auto Scaling groups, ECS services, Lambda functions, inline targets, a classic load balancer's instances), and `internet -> lb` where a group of the load balancer admits the world or an internet-facing network load balancer has no group.
  CloudFront to its origins, API Gateway to the functions its integrations and Lambda permissions name, Lambda function URLs without authorization, public buckets and public EKS endpoints are entered from the internet.
  An Auto Scaling group runs the instances of its launch template and an ECS service runs its task definition, so the role of the instances or tasks can be followed.
  Kubernetes: the Ingress and Service flows, the Secrets a workload reads, the ServiceAccount it runs as, the Role a binding gives that account and the Secrets the role may read within the binding's scope, derived from the properties on the nodes, so manifests in different files join (the parser links one file only).
  A binding to the built-in `cluster-admin` role is reached itself.
  MCP: an enabled server that ingests untrusted content, and a remote server, is entered from the internet; the parser's edges carry the content through the agent to the servers that read private data.
  A remote server of unknown capability is a `definite: false` entry.
- **Reachability facts merge.**
  `InfraGraph.add_reachability_edge` is the way a pass adds one.
  A second fact about a pair (a security group rule and a load balancer target, two rules with different ports) merges into the existing edge: ports and `via` are unions, `world_open` is true if either is, `definite` is false if either is, and `sources` lists every contributor.
  What a parser stated on an edge is never overwritten.
- **A fan-out limit per reachability rule.**
  A rule adds at most 500 edges (`InfraGraph(max_fanout=...)` or `THREATCODE_MAX_FANOUT`), and the build records one `graph.edge_cap` warning that names the rules cut, because a truncated walk can hide a path.
- **The synthetic internet node.**
  `InfraGraph.internet_node` returns it, `ensure_internet_node()` adds it and `InfraNode.is_internet` and `is_synthetic` test for it.
  It has resource type `internet`, zone `internet`, category `network` and exposure `internet`, and mode `data`: the engine runs no rule on it and does not count it in `scanned_resources`, and `InfraGraph.node_count` leaves it out.
  A node the input declares with the id `internet` is that node instead.
- **Contextual severity (`engine/severity.py`).**
  A finding gets an `effective_severity` and a `severity_reason` when context changes it, and the base severity is never touched.
  One level up when the finding is a spoofing, tampering, information disclosure or elevation of privilege finding on a resource the internet reaches over network flows, and the reason names the route (`internet -> aws_lb.front -> aws_instance.app[0]`).
  One level up for any finding on a data store tagged `DataClassification` or `Compliance` with `confidential`, `restricted`, `pci`, `phi`, `hipaa` or `pii` (keys and values without regard to case, `PCI-DSS, HIPAA` holds two classes, `non-pii` holds none).
  One level down, never below `info` and never silenced, for an exposure finding on a resource tagged `Public=true`, `Intent=public` or `threatcode:intent=public`, with `marked intentional` in the reason.
  The changes add up, stop at `critical`, and a finding that would not change gets nothing.
  A finding that states the exposure itself is not raised by reachability, and the root cause of the rule (or, for a rule without one, the words of its id) says which those are.
  Rule, secret and scanner findings are judged; boundary and LLM findings are left alone.
- **Boundary threats from the traffic the reachability pass found.**
  An AWS input produces boundary threats again, now from real flows with the port and protocol in the description (`Traffic from aws_lb.front (dmz zone) to aws_instance.app[0] (private zone) over tcp/8080 crosses a trust boundary`).
  A crossing that starts at the internet node is anchored on the resource it enters, which has a file and a line, and says where it comes from in the title and in `metadata.flow.source`.
  `metadata.boundary_rule` names the kind (`BOUNDARY_UNAUTHENTICATED_FLOW`, `BOUNDARY_UNENCRYPTED_FLOW`, `BOUNDARY_UNVALIDATED_FLOW` for a flow declared `validated: false`, `BOUNDARY_GENERIC_FLOW`) and `metadata.fingerprint_hint` names both ends, so a baseline that accepts the flow from a load balancer to one instance does not accept its flow to another.
  A protocol of all traffic is worded as such, and edges that disagree on the protocol list all of them.
- `AttackPath.alternatives`, emitted only when it is not zero.
- `InfraEdge.source_kind`, `world_open`, `definite`, `ports` and `protocols`, and `ir.edges.REACHABILITY_SOURCES`.
- New diagnostic code `paths.search_truncated`.

### Changed
- **Breaking: `--fail-on` can now fail on an attack path.**
  The gate already read attack paths and effective severities, and both exist now.
  With the default `--fail-on high`, a scan of an input with a public bucket, or with a path from the internet to a database, exits 1.
  A reachable weakness can be one level worse than its rule says, and `--fail-on none` never fails on findings.
- **`InfraGraph.node_count` leaves out the synthetic internet node**, so it still counts what the input defines and equals `scanned_resources` for an input without data sources.
  `graph.nodes` and `to_dict()` include it.
- **`reachability_subgraph()` includes the internet node** whenever some edge needed it, and its edges carry `source`, `ports` and the rest as attributes.
- **A Secrets Manager policy in the aws-webapp example names the secret by its ARN with the six character suffix** (`secret:orders/db-a1B2c3`) instead of the pattern `orders/db-*`.
  The IAM linker reads a trailing `-*` as part of the secret's name and so did not link the role to the secret; see the notes for the package that owns `ir/iam.py`.
- The mitre module documents that `BOUNDARY_TECHNIQUES` and `BOUNDARY_TACTICS` are no longer read by the boundary phase.
  They stay in `engine/mitre.py` because `tests/test_engine/test_mitre.py` pins them there.
