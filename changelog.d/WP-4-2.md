### Added
- **`--ingest` reads the results of the scanners you already run.**
  `threatcode scan PATH --ingest report.json` accepts Trivy JSON, Grype JSON, OSV-Scanner JSON and SARIF 2.1.0 from any tool (Checkov, Gitleaks, Trivy config and others), repeated as often as you like.
  The format is detected from the content, not the file name.
  Each finding becomes a finding of source `scanner` with `evidence` `scanner`, the `tool`, a rule id such as `trivy:CVE-2022-37434` and the other identifiers of the issue in `aliases`.
  A report with nothing in it (Trivy with no results, Grype with no matches, an empty SARIF run) is a valid report with zero findings.
  A file that is unreadable, not JSON, a directory, over 256 MB or not a recognized scanner result exits 2 with an error that names the file and the supported formats.
- **A critical CVE on an exposed workload now sits on that workload.**
  A finding is joined to the graph by the first key that matches.
  Image findings (Trivy and Grype image scans, OSV-Scanner image sources) match the container image references that workloads hold, compared by registry, repository, tag and digest with Docker Hub names normalized, so `nginx:1.25` equals `docker.io/library/nginx:1.25` and a digest decides when both sides have one.
  The references are read from Kubernetes workloads (and so from rendered Helm charts), ECS task definitions, Lambda `image_uri`, the `image` of any other resource, the commands in instance and launch template `user_data` (base64 is decoded) and the base image of each Dockerfile stage, where a CVE in a base image attaches to the `dockerfile_stage` node.
  Findings that name a file and a line (misconfigurations, secrets, SARIF results) attach to the resource whose source span holds the line, in any format.
  Package vulnerabilities in a lockfile or manifest attach to the workloads of the same directory: the final stage of each Dockerfile there and the Kubernetes workloads.
  A finding that runs on several nodes becomes one finding per node, so each node's severity and attack paths see it.
- **Nothing is dropped silently.**
  A finding that no key places is kept with an empty resource address and counted in an `ingest.unattached` diagnostic.
  The diagnostic is a warning, and so a coverage gap that `--strict` turns into exit 2, when a file attached none of its findings, which usually means the report belongs to a different scan; it is info when only some findings did not attach.
  Entries a tool itself set aside (passed Trivy checks, Grype ignored matches, SARIF results marked suppressed or passed, Trivy licenses) are counted under `skipped` in the source record.
  `ScanResult.ingest_sources` lists, for each tool run in each file, the `tool`, `version`, `format`, `file` and the counts `findings`, `attached`, `unattached` and `duplicates`.
- **Severities from the tool, mapped the same way for every tool.**
  Critical, high, medium and low map to themselves, and Trivy `UNKNOWN`, Grype `Negligible` and `Unknown` and an OSV advisory with no rating map to info.
  A score (CVSS base score, SARIF `security-severity`, OSV `max_severity`) maps through the bands 9.0, 7.0 and 4.0.
  A SARIF result without a score maps through its level: error is high, warning medium, note low.
  An OSV advisory that has only a CVSS v3 vector is scored here.
- **A CVE or GHSA id in `.threatcodeignore` suppresses a scanner finding.**
  The `aliases` of a finding hold its own id first and then every other identifier (the CVE behind a GHSA match, a rule's second id), so `CVE-2021-23337` suppresses it whichever tool reported it, and the gate is computed after the suppression.
  This closes the two halves of the old vulnerability-ignore audit item: the ids a finding carries all take part in the match, and a fully suppressed scan exits 0.
- **The same advisory from two tools is one finding.**
  When two ingested tools report the same advisory on the same package of the same node, the first tool keeps its finding, takes the other's ids as aliases and lists the other tool in `metadata.corroborated_by`, with an `ingest.duplicate` info diagnostic.
  `threatcode.ingest.reconcile_native(external, native)` does the same against ThreatCode's own secret and rule findings at the same file and line.

### Changed
- **Secrets in a scanner result are never copied.**
  The matched text of a Trivy secret and the snippet of a SARIF secret are not read, so a report ingested into a ThreatCode result cannot leak the value.
- **Golden recordings are unchanged.**
  No golden input ingests scanner results.

### Notes for integration
- The expectation that the CVE is an enabler of a hop of `internet-to-customer-data` in `tests/test_examples_ingest.py` is marked pending on the attack-path package: the ingested finding is on the instance the path crosses, and the path search must list it in `enabled_by` with an id that contains the CVE (the rule id `trivy:CVE-2022-37434` or an alias).
- The expectation that the JSON report lists the ingested sources is marked pending on the report writer: `ScanResult.ingest_sources` is complete, and `ThreatReport.to_dict` does not write it yet.
- Dropping a scanner finding in favor of a native one needs the native findings, which exist only after the rule engine runs, so the pipeline must call `reconcile_native` after the engine and after locations are made root-relative.
