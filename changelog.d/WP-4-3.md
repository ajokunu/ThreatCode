### Added
- **SARIF that GitHub code scanning can place, remember and rank.**
  Every result points at the file the resource is defined in, as a root-relative, percent-encoded `uri` with `uriBaseId` `%SRCROOT%`, and at its `region` (the input file and line 1 when the line is not known).
  The resource address is never a URI any more.
  It is a `logicalLocation` of kind `resource` and keeps its exact spelling, so `a["prod east"]` and `a["prod-east"]` stay two resources.
  Each result carries `partialFingerprints` `{"threatcode/v1": <fingerprint>}`, so editing a file no longer closes one alert and opens another, and the same address in two files is two alerts.
  Two results that would share a fingerprint, such as two crossings from one load balancer in one zone pair, are told apart by their finding id so GitHub does not merge them.
- **Stable SARIF rules with a severity GitHub understands.**
  A trust boundary crossing uses one rule per zone pair (`THREATCODE_BOUNDARY_INTERNET_DMZ`), a finding from the LLM uses `THREATCODE_LLM`, an ingested scanner finding uses `<tool>:<id>` and a secret keeps its `SECRET_*` id, so a scan with hundreds of crossings has a handful of rules.
  The rule description is generic and the resource-specific text is in the result message.
  Every rule has `security-severity` (critical 9.5, high 8.0, medium 5.5, low 3.0; none for info) taken from the effective severity, and the highest one among the rule's results when they differ.
  `precision` follows the finding's confidence (0.9 and above high, 0.6 and above medium, below that low; always low for the LLM), tags are capped at ten and include `external/cwe/cwe-N` when a rule declares a CWE, and `help.markdown` links the ATT&CK techniques and is left out when there is nothing to say.
  Rule names are letters and digits only, and acronyms such as IAM, RDS and S3 keep their case.
- **SARIF says whether the scan completed.**
  `invocations[0].executionSuccessful` is false when an input could not be read, a rule failed or the LLM step failed, and `toolExecutionNotifications` carry each input error (error), coverage gap (warning or note), failed-rule count and LLM failure (warning), so a partial scan never looks like a clean one.
  The run has `automationDetails.id` `threatcode/<input>/` so scans of different inputs do not overwrite each other's alerts, the driver has a `semanticVersion`, and `$schema` is the SchemaStore URL.
- **Attack paths in SARIF.**
  Each attack path is one result with rule `THREATCODE_ATTACK_PATH`, a level from the path severity, a related location for every hop and a code flow whose steps are the hops' definitions (file and line when the graph knows them, the resource alone otherwise).
  Findings that sit on a path carry `attack_path_ids`.
- **LLM results are advisory in SARIF.**
  They are tagged `advisory`, carry `properties.advisory`, and the model's mitigation is never in the plain message text; it is in `message.markdown`, escaped, and marked as a suggestion.
- **Markdown written to be posted as a pull request comment.**
  The report starts with its title and a hidden marker line, `<!-- threatcode-report -->`, so a CI step can find its own comment and edit it in place.
  Then come a verdict line (`3 critical, 14 high, 2 attack paths from the internet to data`), the severity table, the attack paths (ordered hops with zones, edge types and the findings that enable each hop, plus a Mermaid flowchart with the trust zones as subgraphs), a table of the ten top risks, the findings in STRIDE order (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) and a coverage section that lists input errors, gaps, what was suppressed or baselined and the LLM status.
  Findings that share a root cause on one resource are one entry with a sub-bullet each, and the totals show both counts.
  Technique ids link to attack.mitre.org.
  The report is capped at 60000 characters, under GitHub's 65536 limit: the most severe findings are kept and a footer says how many were left out.
  It has no timestamp when the scan was run with `--no-timestamp`, so two runs over one input produce one comment.
- **A `mermaid` output format.**
  `threatcode scan -f mermaid` draws the resources an attacker can act through, with each trust zone as a subgraph and the attack paths in thick red edges.
  Node ids are generated and labels are quoted, entity-encoded and capped, so a hostile resource name cannot add a statement to the diagram.
- **A terminal report with a verdict and a table.**
  `-f text` starts with `Verdict: 3 critical, 14 high, 2 attack paths from the internet to data`, lists the attack paths, then a table (severity, resource, rule, finding, STRIDE, ATT&CK, location) sorted most severe first.
  The table fits the terminal (`COLUMNS`, the terminal width, or 100 columns when output is redirected): it drops STRIDE, then the technique ids, then the location on a narrow terminal, cuts long cells with `...` and keeps the end of a long address.
  Findings that share a root cause on one resource are one row.
  It always ends with the coverage block, the suppressed and baselined counts and the LLM status.
- **ATT&CK Navigator layers that load.**
  The format is now called `navigator`; `matrix` still works as an alias.
  There is one entry per (technique, tactic) with the tactic's Navigator shortname, so a technique in two tactics appears in both and an entry never has an empty tactic.
  The `IaaS` platform filter is gone, so Docker, Kubernetes and MCP techniques are visible.
  `layout.expandedSubtechniques` is `annotated`, the Navigator version is a full `5.1.0`, `versions.attack` is the bundled ATT&CK release, a revoked technique id is mapped to its replacement, and an id ATT&CK does not know is kept with a warning and listed in the layer metadata instead of being dropped.
  Techniques of attack paths are in the layer with their own comment.
- **Bitbucket annotations on real files.**
  Each annotation has the file and line of the resource, or the input file and line 1, never a resource address.
  Annotations are sorted most severe first and capped at Bitbucket's 1000 per report, with the number left out in the report details, and `annotation_batches` holds them in lists of at most 100 for the bulk endpoint.
  The report data counts Low and Info too, and attack paths are annotations on the first resource of the path that has a file.
- **`threatcode diff` lists attack paths first.**
  Attack paths that appeared or were closed are compared by id and listed before the threats in every format, and `--fail-on-new` also fails on a new attack path at or above the severity.
- **Optional extras in the JSON report.**
  `render("json", analysis, RenderOptions(include_graph=True))` adds `graph` (nodes and edges without properties), `summary_base` (findings by base severity) and `ingest` (the ingested scanner sources).
  `AnalysisResult` gained `root` and `ingest_sources` for them.

### Changed
- **Markdown severities are text labels, not emoji shortcodes.**
  `[CRITICAL]`, `[HIGH]`, `[MEDIUM]`, `[LOW]` and `[INFO]` replace `:red_circle:` and the others in the summary table and in every heading, so the report reads the same in Slack, GitLab and a terminal.
  Each heading names the resource, so repeated titles are told apart.
- **Text from the scanned input can no longer inject Markdown.**
  Titles, descriptions, mitigations and resource names go through two helpers.
  `md_inline` collapses newlines, drops block markers at the start, escapes the characters Markdown treats as syntax, and breaks `@mentions`, `#123` issue references and bare URLs with a zero-width joiner.
  `md_code` fences a resource address with a backtick run longer than any inside it, so `module.net.aws_instance.web["a"][0]` shows literally.
  A blank line plus `## heading` in a mitigation stays inside its blockquote.
  `->` and parentheses are no longer escaped, and underscores inside identifiers such as `aws_flow_log` are left alone.
  The diff report uses the same helpers.
- **The `text` report has a new layout.**
  The per-severity count line is the verdict line, and findings are a table instead of one line each.
  The first line, `ThreatCode scan of <input>: N resources, M findings`, and the coverage block are unchanged.
- **`-f json` writes sorted threats.**
  Threats are in severity order whatever the order the engine produced them in.
  A scan from the CLI or `threatcode.scan()` was already in that order, so its output is unchanged.

### Deprecated
- **The `matrix` format name.**
  It is an alias of `navigator` and will be removed in a later release.

### Golden recordings
- None changed.
  The formatters do not change the analysis, and `tests/test_ir/test_golden.py` passes unchanged.
