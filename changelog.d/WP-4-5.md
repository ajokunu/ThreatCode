### Changed
- **The GitHub Action can fail a build.**
  The scan used to end with `|| true`, so no finding and no error could ever fail a job.
  Now the exit code of `threatcode scan` is captured and exposed as the `exit-code` output.
  Exit 2 (an unreadable path, a file that failed to parse, nothing to scan, a bad option) fails the job at once and the annotation carries the message from stderr.
  Exit 1 (a finding or attack path at or above `fail-on`) does not stop the scan step: the report is written, the SARIF upload runs, and the last step of the action fails the job.
  `fail-on` defaults to `none`, so adopting the action still reports without breaking a build until you ask it to.
  Set `fail-on: high` to gate, which matches the CLI default.
- **The Action installs the code at its own ref.**
  `pip install threatcode` is gone.
  The action installs the checkout it was loaded from (`$GITHUB_ACTION_PATH/../../..`), so `uses: ajokunu/ThreatCode/.github/actions/threatcode@v0.9.1` runs 0.9.1 whether or not the name is registered on PyPI.
  The optional `version` input installs `threatcode==VERSION` from PyPI instead.
  The value is validated before pip sees it.
- **The SARIF upload step works.**
  It was pinned to a commit of `github/codeql-action` that does not exist, so every run with `format: sarif` failed at the upload.
  It is now pinned to the commit of tag `v3.38.2` (checked with `git ls-remote` and an HTTP 200 on the commit).
  The upload runs with `if: always()` whenever a SARIF file exists, so findings reach Code Scanning even when the gate fails the job.
  The new `upload` input (default `true`) turns it off for jobs that have no `security-events: write` permission.
- **The Action handles real paths and every format.**
  Arguments are built as a bash array, so a path, config file or rule file with spaces works.
  `path` takes a file or a directory, and several on separate lines; `input-file` still works as a deprecated alias.
  `threat-count` and the new `path-count` are computed from a JSON report for every format; they used to be 0 for anything but SARIF.
  The new `report-file` output names the written report (`threatcode-results.sarif`, `.json`, `.md`, `.txt` or `.svg`), so json and markdown output is no longer lost.
  New inputs: `fail-on`, `ingest` (scanner results, one per line), `baseline`, `comment`, `github-token`, `upload`, `version`.
  `extra-rules` takes one rule file per line (commas still separate).
  The removed `no-llm` input is not needed: the LLM is off unless you opt in.
  `python3` replaces `python`, and stderr is shown between `::stop-commands::` markers so a file name from the scanned tree cannot inject a workflow command.
- **Optional sticky pull request comment.**
  With `comment: true` on a `pull_request` event the action posts the Markdown report behind the hidden marker `<!-- threatcode-report -->` and updates that comment on later pushes instead of adding new ones.
  The body is cut below 60000 characters with a note.
  The token, repository, pull request number and body file reach the step only through the environment, and the body is read from a file, never placed on a command line.
  Fork pull requests, read-only tokens and other events skip with a notice instead of failing.
  The calling job needs `pull-requests: write` for the comment and `security-events: write` for the upload.
- **CI runs on every pull request and proves more.**
  `pull_request` has no branch filter, so a pull request onto a feature branch is checked too, and `merge_group` is accepted.
  The test matrix covers Python 3.10 to 3.14 on Linux plus one macOS and one Windows job.
  The whole suite also runs against the lowest `python-hcl2` the metadata allows (4.3.5) and against the 8.x series.
  A new `action` job runs the local composite action on `examples/aws-webapp` with `upload: false` and asserts the outputs, a path with spaces, that `fail-on medium` and `fail-on high` fail the job, that a missing path fails the job, and that `fail-on none` does not.
  A `docs` job runs `mkdocs build --strict`.
  A `lint` job runs `actionlint` over the workflows and `shellcheck` over the composite action's scripts.
  `twine check --strict` runs on the built artifacts.
  The dependency audit also runs every Monday and on demand.
  A weekly job compares the committed ATT&CK tables with the pinned release and with the newest published one; it reports drift and never blocks a pull request.
  The coverage artifact is now `coverage.xml`: the hidden `.coverage` file was silently left out of the upload.
- **Releases are gated on CI.**
  `publish.yml` calls `ci.yml` as a reusable workflow and the build job needs it, so a release cannot be published from a commit whose checks failed or never ran.
  The release tag is checked against the version in the built wheel; the version has one source, `threatcode.__version__`, which setuptools reads.
  A manual run of the workflow uploads the same artifacts to TestPyPI as a dry run.
  `action-self-test.yml` is a manual workflow that runs the action with `version:` set to a released version, to verify the PyPI install route after a release.
- **The wheel smoke test compares instead of counting.**
  The packaged rule files must equal the checkout's rule files and the loaded rule ids must equal the ids in the source, so deleting one rule file can no longer pass a floor.
  `threatcode --version`, `threatcode.__version__` and the wheel metadata must agree.
  It scans `examples/aws-webapp`, proves the core install does not contain `anthropic`, proves `--llm` without the extra exits 2 and names `threatcode[llm]`, then installs the `llm` extra and checks the SDK imports.
  `PYTHON` selects the interpreter (default `python3`), and `make smoke` builds and runs it.
- **Packaging metadata.**
  Python 3.14 is a declared classifier; the suite passes on it.
  The `docs` extra drops `mkdocs-autorefs` and `mkdocstrings` (nothing used them) and caps `mkdocs<2` and `mkdocs-material<10`, because the theme's own build warns that MkDocs 2.0 removes plugins and theme overrides.
  `make lint` also checks formatting, and `make ci` runs the docs build and the wheel smoke test.

### Added
- **A pre-commit hook.**
  `.pre-commit-hooks.yaml` defines `threatcode`, which runs `threatcode scan . --fail-on high` over the whole repository (the hook does not pass changed files, because an attack path can cross files).
  Add `args: ["--fail-on", "critical"]` in your config to change the gate.
- **Dependabot** for the `github-actions` (both the workflows and the composite action) and `pip` ecosystems, weekly and grouped, so SHA-pinned actions stay current.

### Release checklist (owner actions, nothing in the repository can do them)
1. On pypi.org add a pending trusted publisher: project `threatcode`, owner `ajokunu`, repository `ThreatCode`, workflow `publish.yml`, environment `pypi`.
2. On test.pypi.org add the same publisher with environment `testpypi`.
3. Create the GitHub environments `pypi` (with required reviewers) and `testpypi`.
4. Run the `Publish` workflow by hand once (workflow_dispatch) and confirm the TestPyPI upload and the smoke test pass.
5. Merge the documentation wording for the release, then publish a GitHub release tagged `v` plus the version in `src/threatcode/__init__.py` (for example `v0.9.1`).
6. Verify the package is live: `curl -s -o /dev/null -w '%{http_code}' https://pypi.org/pypi/threatcode/json` must print 200.
7. Run the `Action self-test` workflow with the released version.
8. Move the floating tag so the action ref resolves: `git tag -f v0 v0.9.1 && git push -f origin v0`.
9. Until step 6 prints 200, document the install as `pip install git+https://github.com/ajokunu/ThreatCode`, because `pip install threatcode` is a different project or a 404.
