### Added
- **Scoped suppressions with a reason and an expiry.**
  A `.threatcodeignore` line is now `<ID> [resource=GLOB] [file=GLOB] [exp:YYYY-MM-DD] [reason="text"]`.
  `ID` is a rule id, a threat id, a fingerprint, or a CVE or GHSA alias.
  `resource=` is an `fnmatch` glob over the resource address and `file=` one over the root-relative POSIX path of the file, so an entry can accept a rule for one bucket or one directory without hiding it everywhere.
  Before, any scoped entry was skipped with a "not supported yet" warning.
  A `file=` scope never matches a finding that has no location.
  Quote a glob that contains spaces, brackets or quotes.
  An option given twice, a scope with no glob and an option this version does not know all skip the entry with a warning, so a line never suppresses more than it says.
- **Warnings that push entries toward a reason and an end date.**
  An entry without a `reason` is warned with its file and line.
  A global entry (no fingerprint and no `resource=` or `file=`) without an `exp` is warned.
  An entry that names a rule listed in a built-in rule file's `deprecated_ids` warns that the rule was removed or renamed and the line no longer does anything.
  Warnings are advisory and never change what is suppressed.
  They reach stderr through the scan notices.
- **A CI trust notice.**
  When the `CI` environment variable is set and the ignore file lives inside the scanned tree, a notice says that a pull request can edit the file and suppress its own findings, and recommends `--ignore-file` with a path the pull request cannot change.
  A value of empty, `0`, `false`, `no` or `off` counts as not set.

### Added to the module API, not yet reached by `threatcode scan`
These work and are tested in `threatcode.suppressions`, but the scan pipeline does not call them yet (see the next section), so the command line does not use them.
- **Attack path suppression.**
  `apply(threats, ignore, attack_paths=...)` returns `kept_paths` and `suppressed_paths`.
  An entry naming a path id suppresses that path, and with `resource=` it must also match a resource on the path's route.
  A `file=` scope never matches a path.
- **Baselines that cover attack paths.**
  `write_baseline(path, threats, attack_paths)` records an `attack_paths` list beside `entries`, with the id, entry, target and severity of every path, sorted for stable diffs.
  `load_baseline()` returns a `Baseline`, a `frozenset` of fingerprints that also carries `path_ids`, and `apply_baseline_paths()` splits attack paths into the kept and the baselined ones.
  A baseline written before this change has no `attack_paths` key, still loads, and baselines no path.
  The schema name `threatcode-baseline/1` is unchanged because older readers ignore the new key.
- **A report of what the ignore file did.**
  `SuppressionResult.report()` returns the entries applied (id, reason, expiry, ignore file, line, scope, matched count), the entries that matched nothing and the entries that expired, in a form that serializes to JSON.
- **User rule files in the removed-rule warning.**
  `load(..., extra_rule_paths=[...])` also reads the `deprecated_ids` of those rule files.

### Fixed
- Line numbers in suppression notices no longer shift when a line holds a form feed or another character that `str.splitlines` treats as a line break.
  A CRLF file and a file that starts with a byte order mark read the same as a plain one.

### Changed
- `write_baseline()` and `baseline_document()` take an optional `attack_paths` argument, and the baseline document always has the `attack_paths` key.

### Still to wire in the scan pipeline
`src/threatcode/pipeline.py` and `src/threatcode/cli.py` belong to an earlier package, so this change does not touch them.
Until `_finish` passes `attack_paths=report.attack_paths` to `suppressions.apply`, calls `apply_baseline_paths`, gives `write_baseline` the attack paths and reports `outcome.report()`, a path id in `.threatcodeignore` suppresses nothing, `--write-baseline` records no paths and the report does not list the applied entries.
