# Releasing

This page is the checklist for publishing a release.
Steps 1 to 4 are repository checks that anyone can run.
The rest are actions that only the owner of the GitHub repository and the PyPI project can take.

## Before you tag

1. Run the whole gate locally:

   ```bash
   make ci
   ```

   It runs `ruff`, `mypy --strict`, the full test suite with coverage, the dependency audit, `mkdocs build --strict` and the wheel smoke test.

2. Check that the generated documentation matches the code:

   ```bash
   python scripts/gen_docs_counts.py --check
   ```

   If it reports a page as out of date, run `python scripts/gen_docs_counts.py --write` and review the diff.

3. Check that the ATT&CK tables are current with the release they pin (needs the network):

   ```bash
   make mitre-check
   ```

4. Move the Unreleased section of `CHANGELOG.md` under the new version and date, and set `__version__` in `src/threatcode/__init__.py`.
   The version has one source, and the wheel metadata, `threatcode.__version__` and `threatcode --version` must agree, which the smoke test checks.

## Publishing

5. On pypi.org add a pending trusted publisher: project `threatcode`, owner `ajokunu`, repository `ThreatCode`, workflow `publish.yml`, environment `pypi`.
6. On test.pypi.org add the same publisher with environment `testpypi`.
7. Create the GitHub environments `pypi` (with required reviewers) and `testpypi`.
8. Run the `Publish` workflow by hand once (workflow dispatch) and confirm the TestPyPI upload and the smoke test pass.
9. Enable private vulnerability reporting in the repository settings (Settings, Code security, Private vulnerability reporting), because `SECURITY.md` tells reporters to use it.
10. Publish a GitHub release tagged `v` plus the version.
    The `publish.yml` workflow calls `ci.yml` first and refuses a tag that does not match the wheel's version.
11. Verify that the package is live:

    ```bash
    curl -s -o /dev/null -w '%{http_code}' https://pypi.org/pypi/threatcode/json
    ```

    It must print `200`.
12. Run the `Action self-test` workflow with the released version.
13. Move the floating tag so the action ref resolves: `git tag -f v0 v0.9.1 && git push -f origin v0`, with the version you released.

## After PyPI returns 200

Until step 11 prints 200, `pip install threatcode` installs a different project or fails, so every page documents the Git URL install:

```text
pip install "git+https://github.com/ajokunu/ThreatCode.git"
```

When the package is live, change the install lines in `README.md`, `docs/index.md` and `docs/getting-started.md` to `pip install threatcode` and `pip install "threatcode[llm]"`, and delete the sentence that says the package is not published.
`tests/test_docs.py` refuses a bare `pip install threatcode` in a shell block until then; change that test in the same commit.
Replace `@main` in the Action and pre-commit examples with the release tag.

## What the documentation tests protect

`tests/test_docs.py` runs every block marked runnable, parses every `threatcode` command against the real CLI and checks that the counts, tables and benchmark generated by `scripts/gen_docs_counts.py` equal the code.
A release is not ready while it fails.
